# Kubernetes Part 1 스터디 흐름 요약

이 문서는 전체 흐름을 논의하고 수정하기 위한 초안입니다. 흐름 변경은 우선 이 문서에 반영하고, 상세 계획인 [STUDY_PLAN.md](STUDY_PLAN.md)에는 별도 지시가 있을 때 반영합니다. 두 문서는 그전까지 서로 다를 수 있습니다.

- **진행:** 발표자 2명, 총 120분. 참가자는 2인 1조로 실습합니다.
- **방식:** 제공된 skeleton을 먼저 실행해 결과를 확인합니다. 이후 필요한 개념을 배우고, 이미 실행한 리소스와 파일을 살펴본 뒤 같은 파일을 수정하며 개념을 적용합니다.
- **환경:** 로컬 k3s에서 실습하고, 같은 배포를 내부 클러스터에 적용할 때 필요한 차이를 살펴봅니다. 클러스터 설정은 사전에 마칩니다.
- **사전학습**: 스터디 진행 전에 k8s 설치 등 기본설정을 해오는 것으로 전제합니다.

1. **0–10분 · 공동 · 왜 Kubernetes가 필요할까?**

   서버 한 대에 애플리케이션을 직접 배포하거나 Docker 명령으로 컨테이너를 실행할 때, 장애 복구·서버 증설·업데이트·접속 경로를 누가 관리하는지 질문합니다. 서버와 서비스가 늘어나면 이 작업을 여러 머신에서 반복하고 조정해야 합니다. Kubernetes는 원하는 상태를 선언하고 여러 controller가 실제 상태를 그에 맞추도록 하여 이런 운영 작업을 지원합니다.

   반면 클러스터 운영과 리소스 모델을 배우는 비용이 생깁니다. 작은 단일 서버에도 항상 필요한 도구는 아니라는 점을 함께 논의합니다. “서버 하나가 갑자기 사라져도 원하는 수를 유지하려면 무엇이 필요할까?”라는 질문으로 실습을 시작합니다.

2. **10–18분 · A · 제공된 skeleton으로 서버 먼저 실행하기**

   조마다 미리 제공된 workload skeleton을 수정 없이 적용하고 서버 응답을 확인합니다. 이때 Pod에 대한 port-forward와 실습 환경의 역할을 간단히 안내합니다. 매니페스트의 세부 필드를 모두 이해하는 것보다 먼저 이후 계속 다룰 서버의 동작을 확인합니다.
클러스터에 Headlamp (Helm 차트) 기본 장착하도록 (계정에서 토큰 만료 없음으로) -> 클러스터 쉽게 보기

3. **18–33분 · A · Pod, ReplicaSet, Deployment 이해하기**

   방금 실행한 리소스를 조회하며 세 가지의 역할을 구분합니다.

   - **Pod:** 하나 이상의 컨테이너를 함께 실행하는 Kubernetes의 기본 실행 단위입니다.
   - **ReplicaSet:** 지정한 수의 Pod가 유지되도록 관리합니다. Pod가 사라지면 필요한 만큼 새 Pod를 만듭니다. (어차피 직접 선언하지 않고 Deployment를 통해 정의되니, 가볍게 다루기)
   - **Deployment:** 서비스를 배포할 때 실제로 사용하는 것. replica set과의 차이점 중점으로, Pod template이 바뀌면 새 ReplicaSet을 이용해 롤아웃합니다. -> 버전 업그레이드 시 왜 빈 replica set가 있는지

   제공된 Deployment 파일과 실제 Deployment → ReplicaSet → Pod의 `ownerReferences`를 연결해 봅니다. 선언적 API, 원하는 상태와 관찰된 상태, reconciliation, namespace/name과 UID도 이 사례에서 소개합니다. Pod를 삭제하기 전에 결과를 예상하고, 삭제 후 새 Pod의 UID와 복구된 replica 수를 확인합니다.

4. **33–43분 · A · 기존 파일로 replica 수 바꾸기** (실습 X, 예시로 보여주기)

   선언된 replica 수가 원하는 상태이며 실제 상태가 수렴하는 데 시간이 걸릴 수 있음을 설명합니다. 앞에서 실행한 workload 파일의 replica 수를 1개에서 2개로 수정해 다시 적용하고, 원하는 수와 준비된 수를 비교합니다. 명령형 scale과 선언 재적용의 차이는 시간이 허락하면 비교합니다.

5. **43–53분 · A · 같은 서버 업데이트하기**

   Pod template의 변경과 롤아웃을 설명합니다. 기존 workload 파일에서 메시지나 `REVISION`을 수정해 재적용하고, Deployment는 유지되는 동안 ReplicaSet과 Pod가 어떻게 바뀌는지 관찰합니다. 이후에도 클라이언트가 바뀌는 Pod를 찾아야 한다는 문제를 다음 파트로 넘깁니다.

   발표자 예시로 (Headlamp에서) 오류가 발생했을 때 어떻게 뜨는지 보여줍니다.

6. **53–58분 · 공동 · 휴식과 인계**

   조별로 키보드 담당을 바꾸고 Pod·ReplicaSet·Deployment의 관계를 간단히 그려 봅니다. Deployment는 이어지는 실습을 위해 유지합니다.

7. **58–72분 · B · 제공된 Service skeleton 실행하고 이해하기**

   준비된 Service 파일을 먼저 적용하고 클러스터 내부 클라이언트에서 요청합니다. 그다음 Service가 안정적인 접근 지점을 제공하고 label/selector로 Pod를 선택하는 방식을 설명합니다. 이미 적용한 Service 파일, Pod label, EndpointSlice를 비교해 실제 연결 관계를 확인합니다. Service가 내부 서비스들을 서로 연결해주는 endpoint라는 점을 강조합니다.

8. **72–82분 · B · 기존 Service 파일로 장애 만들고 고치기**

   Service가 Pod를 선택하는 방식과 Pod의 정상 동작 여부는 별개임을 설명합니다. 앞에서 적용한 Service 파일의 selector를 잘못된 값으로 바꾸어 재적용하고, label과 endpoint를 살펴 원인을 찾은 뒤 같은 파일을 수정해 복구합니다.

9. **82–96분 · B · 준비 상태에 따라 요청 대상 바꾸기**

   Running과 Ready의 차이, 애플리케이션의 readiness 신호와 readiness probe의 역할을 설명합니다. 기존 workload 파일에서 제공된 probe 설정을 확인하고, Pod 하나의 readiness를 실패시켜 상태와 endpoint condition을 관찰합니다. 새 Service 요청을 보낸 뒤 readiness를 복구합니다.

10. **96–106분 · B · 배포할 앱의 책임 정리하기**

    이미지와 실행 설정, resource requests/limits, SIGTERM과 graceful shutdown을 소개합니다. 기존 파일에서 관련 설정을 찾고, 지금까지 배운 내용을 사용해 서버 메시지나 revision을 다시 수정·배포합니다. 두 replica와 Service 응답이 정상인지 확인합니다. 종료 처리는 설명하고 별도의 종료 실험은 선택 사항으로 둡니다.

11. **106–115분 · 공동 · 내부 클러스터로 가져가기**

    같은 서버 파일을 내부 클러스터에 적용한다면 무엇이 같은지, context·namespace·권한·이미지 접근·변경 경로에서 무엇을 확인해야 하는지 비교합니다. 실제 내부 배포는 배정된 실습 환경과 허용된 경로가 준비된 경우 선택적으로 진행합니다.

12. **115–120분 · 공동 · 마무리**

    각 조가 Pod 교체와 Service 장애에서 관찰한 사실을 설명하고 실습 리소스를 정리합니다.

발표자 A는 **서버가 원하는 상태로 유지되는 과정**을, B는 **준비된 서버로 요청이 전달되는 과정**을 중심으로 각각 준비합니다. 공통 앱의 동작과 매니페스트 계약을 먼저 정하고, 각자 준비한 뒤 함께 리허설합니다.
