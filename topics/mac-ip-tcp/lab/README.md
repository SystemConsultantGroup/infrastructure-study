# MAC / IP / TCP 실습

두 PC가 같은 링크와 라우터를 거쳐 통신하는 과정을 관찰합니다. 이후 TCP 연결을 만들고, 연결이 실패하는 상황을 비교합니다.

```text
PC-A                    Router R                    PC-B
10.77.1.2/24 ── 10.77.1.1 | 10.77.2.1 ── 10.77.2.2/24
```

## 1. 실습 A: PC 두 대 준비하기

터미널 두 개를 엽니다. 각각 `infra-study` 저장소 최상위에서 다음 명령을 실행합니다.

**Mac에서 `nix develop`만 실행한 상태로는 `ip`를 사용할 수 없습니다.** 아래의 PC 접속까지 마친 뒤 2번 실습으로 넘어갑니다.

```bash
nix develop
cd topics/mac-ip-tcp/lab
```

첫 번째 터미널에서 실습 환경을 만들고 PC-A에 접속합니다. `./lab up`은 한 번만 실행합니다.

```bash
./lab up
./lab pc a
```

두 번째 터미널에서는 PC-B에 접속합니다.

```bash
./lab pc b
```

각 터미널의 프롬프트가 `[PC-A 10.77.1.2]`, `[PC-B 10.77.2.2]`로 바뀌었는지 확인합니다. 이후 **A**, **B**로 표시한 명령은 해당 PC 터미널에서 실행합니다.

`(nix:nix-shell-env) Mac:lab ...`가 보이면 아직 Mac 본기계의 터미널입니다. `./lab up`으로 VM을 켜도 현재 셸이 자동으로 PC-A로 바뀌지는 않습니다. 준비가 끝났다면 `./lab up`을 반복하지 말고 `./lab pc a` 또는 `./lab pc b`로 접속합니다.

같은 컴퓨터에서 연 터미널 두 개가 어떻게 서로 다른 IP를 사용할 수 있을까요?

- Q1. `nix develop`을 두 번 실행하면 PC가 두 대 생기나요?

    아닙니다. Nix는 사용할 도구를 준비합니다. `./lab pc a`, `./lab pc b`가 서로 다른 Linux network namespace에 접속합니다. 네트워크 설정은 분리되지만 kernel과 filesystem은 공유합니다. Mac에서는 이를 실행할 Linux VM을 QEMU로 준비합니다.

- Q2. Node.js를 따로 설치해야 하나요?

    수동 설치나 `npm install`은 필요하지 않습니다. Nix가 필요한 버전을 준비합니다. Node는 환경 관리와 오류 재현 보조 코드에서 사용하며, 기본 네트워크 실습은 `ip`, `ping`, `mtr`, `tcpdump`, `ss`, `nc`로 진행합니다. 첫 실행에는 도구와 VM 이미지 다운로드가 발생할 수 있습니다.

## 2. 실습 B: 주소와 다음 홉 확인하기

A의 인터페이스와 주소를 확인합니다.

```bash
ip -br link
ip -br -4 addr
```

목적지에 따라 어떤 경로를 선택하는지 확인합니다.

```bash
ip -4 route
ip route get 10.77.1.1
ip route get 10.77.2.2
ip neigh
```

같은 PC에서 보내는데 목적지에 따라 `via` 표시가 달라지는 이유는 무엇일까요?

- Q3. MAC 주소와 IP 주소는 어디에서 확인하나요?

    `ip -br link`는 인터페이스의 링크 주소를, `ip -br -4 addr`는 IPv4 주소와 prefix를 보여줍니다. A의 IP는 `10.77.1.2/24`이며 MAC 값은 환경을 다시 만들 때 달라질 수 있습니다.

- Q4. B로 보낼 때 `via 10.77.1.1`이 나오는 이유는 무엇인가요?

    이 실습에서 A는 `10.77.1.0/24`에 직접 연결되어 있습니다. 다른 네트워크의 B로 보낼 때는 기본 경로에 지정된 라우터 R을 다음 홉으로 선택합니다. R의 `10.77.1.1` 자체로 보낼 때는 직접 연결 경로를 사용합니다.

- Q5. `ip route get`이 성공하면 상대 PC까지 통신된 것인가요?

    아닙니다. 이 명령은 로컬 커널이 선택할 경로를 조회할 뿐 패킷을 보내지 않습니다. 상대까지 도달하고 응답이 돌아오는지는 별도로 확인해야 합니다.

## 3. 실습 C: ping을 보내고 상대가 받는 것 보기

B에서 먼저 패킷을 관찰합니다. `listening on eth0`가 출력되면 **B는 그 상태로 둔 채 A에서 새로 ping을 보냅니다.** tcpdump를 켜기 전에 보낸 패킷이 나중에 표시되지는 않습니다.

```bash
# B
tcpdump --immediate-mode -l -nn -e -i eth0 'arp or icmp'
```

A에서 같은 링크의 R과 다른 네트워크의 B에 각각 ping을 보냅니다.

```bash
# A
ping -n -c 3 10.77.1.1
ping -n -c 3 10.77.2.2
ip neigh
```

B에 도착한 `echo request`와 B에서 나가는 `echo reply`를 찾아봅니다. R에게 보낸 ping은 왜 B에서 보이지 않을까요?

- Q6. 라우터 R에게 보낸 요청도 B까지 전달되나요?

    목적지가 R 자신의 `10.77.1.1`이면 R이 직접 응답합니다. B로 전달할 요청이 아니므로 B의 캡처에 보이지 않는 것이 정상입니다.

- Q7. A가 B와 통신했는데 이웃 캐시에는 왜 R의 MAC이 있나요?

    A가 현재 링크에서 프레임을 넘길 상대는 R입니다. 최종 IP 목적지는 B여도 첫 프레임의 목적지 MAC은 R의 왼쪽 인터페이스입니다. R은 다음 링크에서 B에게 새 프레임을 보냅니다.

- Q8. ARP가 캡처되지 않으면 잘못된 것인가요?

    이미 이웃 캐시에 주소가 있으면 새 ARP 교환 없이 보낼 수 있습니다. `ip neigh`를 함께 확인합니다. 실습을 위해 실제 사용 중인 네트워크의 캐시를 지우지는 않습니다.

- Q9. ping이 성공하면 B의 웹 서버나 TCP 서비스도 정상인가요?

    해당 시점에 ICMP Echo가 왕복했다는 뜻입니다. 특정 TCP 포트가 열려 있거나 애플리케이션이 정상이라는 뜻은 아닙니다. 반대로 ICMP가 차단되면 서비스가 정상이어도 ping은 실패할 수 있습니다.

B에서 `Ctrl+C`로 캡처를 종료합니다. 반대 방향도 확인합니다. 이번에는 A에서 같은 `tcpdump` 명령을 실행하고, B에서 다음 명령을 실행합니다.

```bash
# B
ping -n -c 3 10.77.1.2
```

확인이 끝나면 A의 캡처도 `Ctrl+C`로 종료합니다.

## 4. 실습 D: 라우터 홉과 TTL 확인하기

A에서 B까지의 홉을 관찰합니다.

```bash
# A
mtr -n -r -c 3 -i 0.5 10.77.2.2
```

이번에는 TTL을 1로 제한하고 같은 목적지로 보냅니다.

```bash
# A
ping -n -c 1 -W 1 -t 1 10.77.2.2
```

목적지는 B인데 왜 R이 `Time to live exceeded`로 응답할까요?

- Q10. `mtr`에 어떤 주소가 나와야 하나요?

    이 실습에서는 첫 홉에 R의 `10.77.1.1`, 둘째 홉에 B의 `10.77.2.2`가 나옵니다. `ip route`가 로컬의 경로 선택을 보여주는 것과 달리, `mtr`는 실제 probe를 보내 응답한 홉을 관찰합니다.

- Q11. TTL을 1로 주면 왜 실패하나요?

    라우터가 패킷을 전달할 때 TTL을 감소시킵니다. R에서 TTL이 소진되므로 R이 패킷을 버리고 ICMP Time Exceeded를 돌려줍니다. 이 실패는 의도한 결과이며, TTL은 패킷이 무한히 순환하는 것을 제한합니다.

- Q12. `mtr`에서 응답하지 않는 홉은 고장난 라우터인가요?

    반드시 그렇지는 않습니다. 장비가 probe 응답을 제한하거나 필터링할 수 있습니다. 응답하지 않는다는 사실만으로 실제 데이터 전달도 실패한다고 단정하지 않습니다.

## 5. 실습 E: TCP로 데이터를 보내고 handshake 확인하기

B에서 TCP 캡처와 `nc` 서버를 백그라운드로 실행합니다. `$!`는 방금 시작한 백그라운드 프로세스의 PID입니다.

```bash
# B
tcpdump --immediate-mode -nn -i eth0 'tcp port 18080' > /tmp/tcp-demo.log 2>&1 &
CAP=$!
printf 'reply-from-B\n' | nc -N -l 10.77.2.2 18080 > /tmp/from-a.txt &
SERVER=$!
ss -ltn 'sport = :18080'
```

`ss`에서 `LISTEN`을 확인한 뒤 A를 실행합니다. 아직 보이지 않으면 `ss`를 다시 실행합니다.

```bash
# A
printf 'hello-from-A\n' | nc -N -w 2 10.77.2.2 18080
```

A의 명령이 끝나면 B에서 받은 내용과 캡처를 확인합니다.

```bash
# B
wait "$SERVER"
cat /tmp/from-a.txt
kill -INT "$CAP"
wait "$CAP"
cat /tmp/tcp-demo.log
```

A에는 `reply-from-B`, B의 파일에는 `hello-from-A`가 있어야 합니다. 데이터가 나오기 전에 TCP는 어떤 패킷을 주고받았을까요?

- Q13. `ss`의 `LISTEN`은 무엇을 뜻하나요?

    해당 주소와 포트에서 연결 요청을 기다리는 소켓이 있다는 뜻입니다. `LISTEN`만으로 이미 클라이언트와 연결되었다고 말할 수는 없습니다.

- Q14. `Flags [S]`, `[S.]`, `[.]`는 무엇인가요?

    일반적인 연결 수립에서 각각 SYN, SYN+ACK, ACK입니다. A의 SYN, B의 SYN+ACK, A의 ACK 순서를 찾아봅니다. 출발지 임시 포트와 sequence 값은 실행마다 달라질 수 있습니다. `.`는 ACK flag이며, 항상 payload 없는 패킷이라는 뜻은 아닙니다.

- Q15. `nc`의 `-l`, `-N`, `-w 2`는 무엇인가요?

    이 실습은 OpenBSD netcat 기준입니다. `-l`은 연결 대기, `-N`은 표준입력이 끝났을 때 송신 방향 종료, `-w 2`는 연결 또는 유휴 timeout 설정입니다. 반대 방향의 데이터를 받는 것과 내 송신 방향을 닫는 것은 구분됩니다.

- Q16. 문자열을 한 번 보냈으면 상대도 반드시 한 번에 읽나요?

    TCP는 메시지 경계가 아니라 순서 있는 바이트 스트림을 제공합니다. 한 번 쓴 내용이 여러 번에 나뉘어 읽힐 수도 있습니다. 메시지 경계는 길이 필드나 구분자 등으로 애플리케이션이 정해야 합니다.

- Q17. TCP ACK가 왔으면 상대 애플리케이션의 처리도 끝났나요?

    ACK는 TCP의 수신 확인이지 업무 처리 완료 확인이 아닙니다. 예를 들어 주문 저장이나 DB commit이 끝났는지는 애플리케이션의 응답으로 확인해야 합니다.

## 6. 실습 F: 실패 원인 구분하기

### 6-1. 연결을 받을 서버가 없는 경우

앞 실습의 `nc` 서버가 종료된 상태에서 A에서 실행합니다.

```bash
# A
ping -n -c 1 10.77.2.2
nc -vz -w 2 10.77.2.2 18080
```

ping은 성공하는데 TCP 연결이 거절되는 이유는 무엇일까요?

- Q18. `Connection refused`는 B에 도달하지 못했다는 뜻인가요?

    보통 명시적인 거절 응답을 받았다는 뜻입니다. 이 실습에서는 해당 포트에 listener가 없습니다. 운영 환경에서는 방화벽 등의 명시적 거절도 원인이 될 수 있으므로 오류 문자열만으로 원인을 확정하지 않습니다.

### 6-2. 연결은 받지만 응답하지 않는 경우

이후 실습의 `listen`, `send`, `drop-demo`는 제공된 **오류 재현 함수**입니다. 표준 Unix 명령은 아니며, 실제 TCP socket과 격리된 라우터의 iptables를 사용해 조건을 일정하게 만듭니다.

B에서 연결을 받되 애플리케이션 응답을 보내지 않는 서버를 실행합니다.

```bash
# B
listen hold
```

```bash
# A
send hello
```

`CONNECTED`가 나온 뒤 `READ_TIMEOUT`이 나오는 이유는 무엇일까요?

- Q19. 읽기 timeout은 연결 handshake부터 실패했다는 뜻인가요?

    아닙니다. 이 결과에서는 연결 수립은 완료됐지만, 클라이언트가 기다린 애플리케이션 응답이 정해진 시간 안에 오지 않았습니다. 연결 단계의 timeout과 구분해야 합니다.

B에서 `Ctrl+C`로 서버를 종료합니다.

### 6-3. 연결 후 강제로 중단하는 경우

B에서 데이터를 받으면 연결을 reset하는 서버를 실행합니다.

```bash
# B
listen reset
```

```bash
# A
send hello
```

연결이 된 뒤 `ECONNRESET`이 발생하는 이유는 무엇일까요?

- Q20. reset은 정상 종료와 무엇이 다른가요?

    정상 종료는 FIN을 이용해 송신 방향의 종료를 알립니다. RST는 연결을 비정상적으로 중단하는 신호입니다. 이 실습은 B가 의도적으로 reset하지만, 운영 환경에서는 중간 장비도 원인이 될 수 있습니다.

B에서 `Ctrl+C`로 서버를 종료합니다.

### 6-4. 중간에서 패킷을 버리는 경우

B에서 정상 응답 서버를 실행합니다.

```bash
# B
listen echo
```

A에서 R이 특정 TCP 흐름을 잠시 버리도록 한 뒤, 복구 여부를 확인합니다.

```bash
# A
drop-demo
send restored
```

같은 서버인데 처음에는 `CONNECT_TIMEOUT`, 그다음에는 `SUCCESS`가 나오는 이유는 무엇일까요?

- Q21. `drop-demo`는 무엇을 바꾸나요?

    R의 실습 namespace 안에서 A→B TCP 18080 흐름만 일시적으로 DROP합니다. 종료할 때 규칙을 제거하므로 이어 보낸 요청은 정상 응답할 수 있습니다. Mac이나 호스트의 방화벽은 변경하지 않습니다.

- Q22. timeout은 항상 방화벽 문제인가요? 왜 2초인가요?

    응답이 없다는 사실만으로 방화벽을 단정할 수는 없습니다. 경로·상대 상태 등 여러 원인이 가능합니다. 여기서는 우리가 넣은 DROP이라는 조건을 알고 있습니다. 2초는 이 클라이언트의 deadline이며 kernel TCP 재전송의 최종 한도가 아닙니다.

`send restored`까지 성공했는지 확인합니다. `CLEANUP_ERROR`가 나오면 실습을 중단하고 환경을 종료한 뒤 다시 만듭니다.

## 7. 실습 환경 종료하기

B의 서버를 `Ctrl+C`로 종료합니다. A와 B에서 각각 `exit`로 PC 셸을 나온 뒤, 일반 Nix 터미널 한 곳에서 실행합니다.

```bash
./lab stop
```

- Q23. VM 이미지와 도구도 모두 삭제되나요?

    아닙니다. 실습 프로세스와 namespace, Mac의 실습 VM을 종료합니다. 다음 실행에서 재사용할 이미지와 도구는 남습니다. 다시 시작할 때는 `./lab up`을 실행합니다.
