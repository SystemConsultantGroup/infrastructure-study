# HTTP / TLS / DNS

[전체 커리큘럼으로 돌아가기](../../README.md)

## 기본 정보

- **대상:** 애플리케이션 개발자
- **담당 인원:** 2명
- **시간:** 120분

## 학습 목표

이름을 주소로 해석하고, 통신 상대를 신뢰하며, HTTP 요청과 응답을 주고받는 과정을 하나의 흐름으로 이해합니다.

각 프로토콜의 세부 형식을 외우기보다 DNS, TLS, HTTP가 해결하는 문제와 서로의 책임 경계를 설명할 수 있는 것이 목표입니다.

## 준비 방향

대표적인 웹 요청 하나를 따라가거나 여러 짧은 사례를 비교하는 등 구성 방식은 자유입니다. 프로토콜의 등장 배경과 애플리케이션 개발자에게 중요한 의미를 중심으로 준비합니다.

아래 질문은 가능한 탐구 방향입니다. 세션의 흐름에 맞지 않는 항목은 줄이거나 다른 사례로 바꿀 수 있습니다.

## 탐구 주제

### 전체 요청 흐름

- URL에서 응답까지 어떤 시스템과 프로토콜이 관여하는가?
- 항상 필요한 단계와 캐시하거나 재사용할 수 있는 단계는 무엇인가?
- 프록시, 게이트웨이, CDN 등이 추가되면 책임과 신뢰 경계는 어떻게 달라지는가?

### DNS

- 이름과 주소를 분리하면 어떤 문제를 해결할 수 있는가?
- DNS의 권한은 어떻게 분산되고 위임되는가?
- 재귀 리졸버, 권한 있는 DNS 서버, 캐시는 각각 어떤 역할을 하는가?
- 같은 이름에 대해 서로 다른 결과가 나타날 수 있는 이유는 무엇인가?

### TLS

- TLS는 어떤 위협을 다루며, 무엇까지 보장하는가?
- 인증서와 신뢰 사슬(chain of trust)을 통해 서버의 신원을 어떻게 확인하는가?
- SNI와 ALPN은 어떤 필요에서 등장했는가?
- TLS 종료 지점이 달라지면 누가 어떤 구간을 신뢰해야 하는가?

### HTTP

- HTTP 메서드, 상태 코드, 헤더는 요청의 의도와 결과를 어떻게 표현하는가?
- 안전성, 멱등성, 캐싱은 API 설계와 어떤 관련이 있는가?
- 쿠키와 CORS는 브라우저의 상태 및 보안 모델과 어떻게 연결되는가?
- 프록시를 통과한 정보 가운데 애플리케이션이 신뢰해도 되는 것은 무엇인가?

### 프로토콜 변화와 실패 구분

- HTTP/1.1, HTTP/2, HTTP/3는 어떤 문제를 해결하기 위해 발전했는가?
- 전송 방식이 달라져도 유지되는 HTTP 의미 체계는 무엇인가?
- DNS, 전송 계층, TLS, HTTP, 애플리케이션의 실패를 어떻게 구분할 수 있는가?
- 관찰된 오류만으로 결론 내릴 수 없는 부분은 무엇인가?

## 범위

### 핵심 범위

- DNS, TLS, HTTP가 이어지는 전체 흐름
- DNS의 위임과 캐시
- TLS의 신원 확인과 신뢰 모델
- 애플리케이션에 중요한 HTTP 의미 체계
- HTTP 버전이 등장한 배경
- 실패가 발생한 영역을 구분하는 방법

### 범위 밖

- 패킷 캡처 심층 분석
- 암호 알고리즘과 TLS 메시지 형식의 세부 구현
- 모든 DNS 레코드 소개
- HTTP 프레임 구조 암기
- 프로토콜별 상세 성능 비교
